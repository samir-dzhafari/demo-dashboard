# Дашборды сети филиалов

Два дашборда для сети из 7 филиалов: управленческий «Операционная сводка» и маркетинговый «Маркетинг и продажи».
Бэкенда нет: все данные генерируются в рантайме детерминированным мок-генератором.

Источник правды — `docs/ТЗ_на_дашборды_управленческий_и_маркетинговый.docx`, визуальные референсы — `docs/screenshot-*.jpg`.

**Статус: сессия 4 из 4 — готово.** Обе страницы (`/operations`, `/marketing`) собраны, критерии приёмки ТЗ проверены тестами, см. раздел «Что реализовано по ТЗ».

Виджеты `/operations` (`src/widgets/*`, данные из `getDataset()` + `shared/lib/metrics`, фильтры из store):

## Архитектура (FSD)

```
src/
  app/        инициализация: провайдеры, роутер, store, глобальные стили
  pages/      страницы operations и marketing: сборка виджетов в сетку
  widgets/    самостоятельные блоки страниц (ui + model-хук на каждый)
  features/   пользовательские сценарии (filters)
  entities/   бизнес-сущности: типы данных в model/types.ts
  shared/     переиспользуемое: api/mocks, lib/{date,format,metrics}
```

### Правило импортов: только вниз

Слой может импортировать только из слоёв **ниже** себя: `app → pages → widgets → features → entities → shared`.
Импорты вверх и между слайсами одного слоя запрещены (внутри слайса — относительные пути, наружу — только через `index.ts`).
Правило проверяет ESLint (`@typescript-eslint/no-restricted-imports`, см. `eslint.config.js`), `npm run lint` падает при нарушении.

**Единственное исключение — «контракт данных».** Типы по условию лежат в `entities/*/model/types.ts`, а мок-генератор
(`shared/api/mocks`) и вычисления, пересекающие несколько сущностей (`shared/lib/metrics`), обязаны их описывать.
Поэтому в этих двух папках разрешён **только `import type`** из `entities`. Значения из `entities` в `shared` импортировать нельзя.

Алиасы: `@/app`, `@/pages`, `@/widgets`, `@/features`, `@/entities`, `@/shared` (настроены в `tsconfig.json` и `vite.config.ts`).

## Redux Toolkit

| Что | Где |
|---|---|
| Конфиг store, `RootState`, `AppDispatch` | `src/app/store/store.ts` |
| Типизированные `useAppDispatch`, `useAppSelector` | `src/app/store/hooks.ts` |
| Обёртка `<StoreProvider>` над `<Provider store>` | `src/app/store/Provider.tsx` |
| Слайсы | `features/*/model` или `entities/*/model` (рядом с логикой), в store подключаются в `app/store/store.ts` |
| Селекторы | рядом со слайсом (`model/selectors.ts`), мемоизированные — через `createSelector` из `@reduxjs/toolkit` |

Соглашения:

- В компонентах **не использовать** «сырые» `useDispatch` / `useSelector` — только `useAppDispatch` / `useAppSelector`.
- Слайсы и селекторы не импортируют `RootState` из `app` (это был бы импорт вверх). Селектор принимает форму `{ filters: FiltersState }`.
- Redux DevTools включены автоматически самим `configureStore` в dev-режиме.
- Сейчас в store один слайс — `filters` (`features/filters`): период `{kind, from, to}` (по умолчанию с начала года по вчера),
  филиалы и каналы (по умолчанию выбраны все; пустой выбор игнорируется), база сравнения `yoy | plan`. Без него store остался бы пустым, а Redux предупреждает о пустом редьюсере. Селектор
  `selectMetricFilters` отдаёт состояние в формате `MetricFilters`, который принимают функции метрик.

## Мок-генератор (`shared/api/mocks`)

Публичный API: `getDataset(): Dataset` (синхронно, один раз на загрузку, потом кэш) и `generateDataset(seed)` для тестов.
Тот же seed даёт те же данные. Генерация занимает около 0,7 с, в памяти порядка 1 млн объектов.

**Справочники:** 7 филиалов (Центральный, Северный, Южный, Западный, Восточный, Речной, Парковый), 5 направлений услуг
(по 3 услуги в каждом), 6 каналов, 62 ресурса (кабинеты/оборудование/специалисты).

**Период:** 22 месяца, с 2025-01-01 по 2026-10-28 («вчера» демо-даты 2026-10-29). Планы заведены на 24 месяца, до декабря 2026.

**Шесть наборов данных ТЗ:**

| Набор | Поле `Dataset` | Сортировка | Строк (≈) |
|---|---|---|---|
| Записи и визиты | `records` | `slotDate` | 417 тыс. |
| Расписание слотов | `slots` | `date` | 537 тыс. |
| Заявки | `leads` | `createdAt` | 136 тыс. |
| Расходы на маркетинг | `marketingExpenses` | `date` | 8 тыс. (день × канал × кампания) |
| Планы | `plans` | — | 168 (филиал × месяц) |
| Веб-аналитика | `webAnalytics` | `date` | 4 тыс. (день × канал) |

Метрики полагаются на сортировку (бинарный поиск по диапазону дат), тесты её проверяют.

**Как устроена генерация.** Согласованность достигается порядком шагов, а не подгонкой итогов:

1. **Слоты и визиты, день за днём.** Для каждого ресурса и часа 8–20 слот доступен с сезонной вероятностью (летом больше простоев).
   Доступный слот занимается с вероятностью «целевая загрузка филиала × сезон × тренд × день недели/час». Отдельно на тех же
   слотах появляются отменённые записи и неявки, их доля зависит от филиала и снижается год к году.
2. **Клиенты.** Визит — это новый клиент (36%) или возвращающийся из пула филиала (с перекосом в сторону недавних). У клиента
   есть уникальный телефон. Первый визит нового клиента может прийти из заявки.
3. **Заявки.** Каждая заявка, приведшая к записи, создаётся вместе с визитом: тот же телефон, `recordId` указывает на запись,
   время заявки раньше создания записи, запись создана раньше слота. Вокруг каждой такой заявки добавляются заявки без записи
   (число задаётся конверсией канала) и дубли того же телефона в течение 1–6 дней (~4%).
4. **Веб-аналитика и расходы** строятся от дневного потока заявок канала, поэтому CPL по каналам близок к ориентиру со скриншота,
   а визиты всегда больше заявок.
5. **Планы** выводятся из факта: у каждого филиала задано «плановое» отклонение (от −8,5% до +6,4%), будущие месяцы
   планируются как прошлый год × 1,115.

**Что заложено в динамику:** рост выручки ~13% г/г (визиты +6%, средний чек +6,6%), рост заявок ~18%, снижение CPL, отмен и неявок,
рост загрузки и доли онлайн-записи; подъём в сентябре–октябре (выше летнего уровня более чем на 15%). Доля пакетов и корпоративного
сегмента растёт.

## Метрики и формулы

Все функции — чистые, живут в `shared/lib/metrics`, принимают `(dataset, filters)` и возвращают число или `null`
(если делить не на что, `NaN` не возвращается). `MetricFilters = { from, to, branchIds?, directionIds?, channelIds? }`;
пустой или отсутствующий список означает «все».

| Метрика (`MetricKey`) | Функция | Формула по справочнику ТЗ |
|---|---|---|
| Выручка (`revenue`) | `revenue` | Σ оплат за визиты «Состоялась» по дате визита − возвраты по дате возврата |
| Оказано услуг (`servicesCount`) | `servicesCount` | число записей «Состоялась» |
| Средний чек (`averageCheck`) | `averageCheck` | выручка ÷ оказано услуг |
| Загрузка (`capacityLoad`) | `capacityLoad` | занятые слоты ÷ доступные слоты × 100% |
| Отмены и неявки (`cancellationRate`) | `cancellationRate` | (отменённые + неявки) ÷ все записи × 100% |
| Выполнение плана (`planCompletion`) | `planCompletion` | выручка факт ÷ выручка план × 100% |
| Лиды (`leads`) | `leadsCount` | уникальные заявки; дубль телефона в течение 7 дней не считается |
| Конверсия в запись (`bookingConversion`) | `bookingConversion` | лиды с созданной записью ÷ лиды × 100% |
| CPL (`cpl`) | `costPerLead` | бюджет ÷ лиды |
| CAC (`cac`) | `customerAcquisitionCost` | бюджет ÷ новые клиенты с визитом «Состоялась» |
| ROMI (`romi`) | `romi` | (выручка первого визита новых клиентов − бюджет) ÷ бюджет × 100% |
| Повторные клиенты (`repeatClientsShare`) | `repeatClientsShare` | клиенты с 2+ визитами за 12 месяцев ÷ все клиенты с визитом × 100% |
| Доля онлайн-записи (`onlineBookingShare`) | `onlineBookingShare` | записи через сайт/виджет ÷ все новые записи × 100% |

Вспомогательные расчёты для виджетов: `branchPerformance` (таблица филиалов), `revenueByDirection` (структура выручки),
`channelEfficiency` (строки каналов и итог, итог считается из сырых данных, а не суммой строк), `acquisitionFunnel`
(5 этапов с конверсией из предыдущего), `byMonth` / `computeMetricSeries` (спарклайны), `compareWithPreviousYear`
(значение, база, дельта и цветовой тон), `computeMetric` / `METRIC_FUNCTIONS` (вызов метрики по ключу).

**Дельты и цвета** (`metricMeta.ts`): `isGoodDelta(metricKey, delta)` истинна, если изменение в хорошую сторону.
Для отмен, CPL и CAC хорошо снижение. `getDeltaTone` дополнительно различает нейтральную дельту (0). `computeDelta` считает
относительную дельту в % для денег и количеств и разницу в п.п. для долей (загрузка, отмены, конверсия, ROMI, повторные, онлайн, план).

**Форматирование** (`shared/lib/format`): `formatNumber`, `formatRub` («2 278 ₽»), `formatMillions` и `formatMillionsRub`
(«412,8 млн ₽»), `formatPercent`, `formatDeltaPercent` («+12,7%»), `formatPercentPoints` («+1,1 п.п.»). Разделитель тысяч —
неразрывный пробел `U+00A0`, десятичный — запятая, минус — `−` (`U+2212`).

## Зафиксированные трактовки

ТЗ оставляет эти места открытыми. Всё ниже — наши решения, их стоит подтвердить у заказчика.

1. **ROMI — по выручке первого визита** (по умолчанию из ТЗ). Выручка нового клиента — оплата минус возврат по записи, созданной из заявки.
2. **«Новый клиент» для CAC и ROMI** — клиент, чья заявка дала запись со статусом «Состоялась». Данные генерируются так, что заявка всегда
   привязана к первому визиту клиента (тест это проверяет). В реальных данных этот инвариант надо проверить первым.
3. **Атрибуция** — «последний значимый канал»: у заявки ровно один канал, расходы и выручка идут в канал заявки.
4. **ROMI** на моках подогнан под скриншот (321% против 312%) за счёт первых визитов: средний первый чек около 5,7 тыс. ₽ (надбавка за первый визит и доля пакетов). См. таблицу выше.
5. **Дата отсчёта.** Выручка, оказано, загрузка, отмены, план — по дате слота; возвраты — по дате возврата. Лиды, бюджет, CPL, CAC, ROMI,
   воронка — по дате заявки. Доля онлайн-записи — по дате создания записи. Диапазон включает обе границы.
6. **Загрузка.** Слот занят, если на нём есть запись «Состоялась». Отмены и неявки слот не занимают. Доступность берётся из расписания;
   фильтр направлений на загрузку и план не действует (у слотов и планов нет направления).
7. **План за неполный месяц** считается пропорционально числу дней периода в этом месяце. Иначе период «с начала года по вчера»
   сравнивал бы 28 дней октября с планом на 31 день.
8. **Повторные клиенты** — окно «12 месяцев» это последние 12 месяцев до конца периода (`to`), начало периода не влияет. Этап воронки «Повторные» —
   клиенты из заявок периода, у которых в том же окне 2+ визита «Состоялась».
9. **Дубли заявок.** Заявка не считается, если у того же телефона уже есть учтённая заявка менее 7 дней назад (учитывается вся история,
   а не только выбранный период, канал дублей не учитывается).
10. **Фильтр «Филиалы» на маркетинговом экране.** В заявках, расходах и веб-аналитике нет филиала, поэтому маркетинговые метрики
    `branchIds` и `directionIds` игнорируют. В ТЗ сказано, что фильтр влияет на все виджеты. Чтобы выполнить это буквально, в реальных данных
    нужен филиал в заявках и расходах. Решить до сессии с маркетинговым дашбордом.
11. **Записи по неполному периоду.** Генерируются только записи со слотом до 2026-10-28, будущие слоты с уже созданными записями не
    моделируются; поэтому число «новых записей» последних дней по дате создания немного занижено.
12. **Недели и месяцы** — см. «Трактовки сессии 4» (реализованы).
13. **Время обновления** (`dataset.meta.updatedAt`) фиксировано: 2026-10-28 23:00.

## Трактовки сессии 3

1. **Файлы скриншотов перепутаны по именам:** `screenshot-operations.jpg` показывает маркетинг, `screenshot-marketing.jpg` — операционную сводку. Использован второй.
2. **Фильтр направления** — новое поле `directions` в `filtersSlice` (пусто = все; клик по сектору включает одно направление, повторный клик сбрасывает; чип над KPI тоже сбрасывает). Планов по направлениям нет, поэтому при активном направлении план-линия графика скрыта, а план/факт по филиалам считает целого филиала.
3. **Сравнение «План»:** выручка сравнивается с планом периода, загрузка — с целью 85%; у остальных метрик плана в ТЗ нет, они остаются «к году назад» (подпись в карточке это показывает).
4. **График по месяцам** показывает год окончания периода; факт идёт до конца периода/данных. Последний неполный месяц сравнивается с прошлым годом и планом за те же дни.
5. **Тепловая карта:** часы 8–20 (13 столбцов) — слоты в данных начинаются с 8 до 20 ч, т. е. покрывают 8:00–21:00. Диапазон — 56 дней до `DATA_END`, независимо от периода.
6. **План/факт по филиалам** сделан div-полосами (не Recharts): нужны клик, плашка отклонения и черта плана в одной строке; остальные графики — Recharts.
7. Плашка плана в таблице красится по округлённому значению, которое на ней написано.

## Трактовки сессии 4

1. **Шапка маркетинга:** период, филиалы, каналы и подпись «Атрибуция: Последний значимый» (не выпадающий список). Фильтр «Сравнение» на маркетинге скрыт: планов по маркетингу нет, дельты всегда к тому же периоду прошлого года. Фильтр «Филиалы» оставлен по ТЗ («влияет на все виджеты»), но реально действует только на «Источники записи»: у заявок, расходов и веб-визитов нет филиала (см. трактовку 10).
2. **«Лиды по неделям»:** 16 последних **полных** недель (пн–вс), заканчивающихся не позже конца периода; начало периода не влияет. Подпись — дата понедельника (дд.мм). Недели из последних 6 дней данных отброшены (`LEAD_LAG_DAYS` в `shared/api/mocks/config.ts`): заявка создаётся за 1–6 дней до визита, а визиты после 28.10 мок не создаёт, поэтому без отсечения график заканчивался бы ложным провалом.
3. **«Источники записи»:** новые записи по **дате создания**, 6 календарных месяцев до месяца конца периода; последний месяц обрезан концом периода. Фильтр каналов не действует (у записи нет канала). Подпись «Доля самостоятельной онлайн-записи в [месяце]» = доля онлайна в последнем месяце, изменение в п.п. — к первому из показанных месяцев. Масштаб осей — по мокам (≈ 20 тыс. записей в месяц, на скриншоте условно 2–3 тыс.: скриншот не согласован с остальными цифрами).
4. **Клик по каналу:** фильтр `channels = [id]`, повторный клик (или чип «Канал: … ✕» над KPI) возвращает все каналы. В таблице остаются только выбранные каналы, строка «Итого» считается по ним же.
5. **ROMI-полоска:** цвет по округлённому числу (≥300% синяя, 200–299% светло-синяя, <200% оранжевая), длина — от 0 до 700% (шкала фиксированная, чтобы строки были сравнимы).
6. **Воронка:** ширина ступеней задана фиксированно (100/84/68/56/44%), а не пропорционально числу — пропорции 1,3 млн к 65 тыс. не читаются. Конверсия «Повторные» = клиенты периода с 2+ визитами ÷ состоявшиеся.
7. **Пустые состояния:** виджеты показывают «Нет данных за выбранный период» вместо нулей и NaN (проверено тестами на периоде без данных).
8. **Адаптив:** от 1280 px и шире сетка как на эталоне (фиксированные высоты рядов), ниже — виджеты встают в одну колонку с фиксированной высотой ряда, KPI идут по 2–3 в ряд, таблица каналов прокручивается внутри карточки, подписи недель на графике прореживаются. Сайдбар на узком экране сужается. Проверено на 775, 1100, 1280 и 1600 px.
9. **Доступность:** глобальное правило `:focus-visible` в `app/styles/index.css`, строки таблиц и этапы воронки доступны с клавиатуры, у заголовков KPI есть тултип с формулой (hover и focus).

## Тесты

`npm run test` (около 10 с, большая часть — генерация датасета). Компонентные тесты (`*.test.tsx`) используют Testing Library и jsdom (`// @vitest-environment jsdom`). Критерии приёмки ТЗ (для месяца, года до даты и произвольного диапазона):

- сумма выручки по филиалам и по направлениям равна общей выручке;
- средний чек = выручка ÷ оказано для сети и для отдельных филиалов;
- сумма лидов и бюджетов по каналам равна итоговой строке;
- каждый этап воронки не больше предыдущего (по сети и по каждому каналу);
- CPL, CAC и ROMI пересчитываются из сырых полей независимой реализацией без расхождений;
- согласованность данных: связка заявка ↔ визит по телефону и времени, только первый визит нового клиента, завершённые визиты только на
  доступных слотах, детерминизм по seed, сортировка массивов, рост 8–18% г/г и осенний пик;
- маркетинговые метрики на маленьком наборе, считаемом вручную (`marketing.test.ts`): дубли лидов, CPL, конверсия, CAC, ROMI с возвратами, `null` вместо NaN, фильтр по каналу в таблице, воронке и метриках;
- тренды (`trends.test.ts`): 16 недель с понедельниками, недели складываются в диапазон, 6 месяцев источников, переход через год;
- страницы (`MarketingPage.test.tsx`, `OperationsPage.test.tsx`): клик по каналу и повторный клик, сортировка, зелёные дельты CPL / CAC / ROMI / отмен, одновременная реакция на период и филиалы, пустые состояния;
- `isGoodDelta` для хороших и плохих метрик, `computeDelta`, форматирование, слайс фильтров и мемоизация селектора.

## Что реализовано по ТЗ

Критерии приёмки (раздел «Критерии приёмки» ТЗ) — каждый закрыт автотестом, кроме последнего, который проверен в браузере:

- [x] Сумма выручки по филиалам равна общей выручке в карточке KPI — `acceptance.test.ts` (месяц, год до даты, произвольный диапазон)
- [x] Средний чек = Выручка ÷ Оказано услуг (сеть и отдельные филиалы) — `acceptance.test.ts`
- [x] Сумма лидов и бюджетов по каналам равна итоговой строке таблицы — `acceptance.test.ts`, `marketing.test.ts`
- [x] Каждый этап воронки не больше предыдущего (сеть и каждый канал) — `acceptance.test.ts`
- [x] Фильтры периода и филиалов меняют все виджеты экрана одновременно — `OperationsPage.test.tsx`, `MarketingPage.test.tsx`. Исключения заданы данными: тепловая карта всегда показывает последние 8 недель (по ТЗ), графики «по неделям» и «по месяцам» берут только конец периода, а у лидов, расходов и веб-визитов нет филиала (см. трактовку 10)
- [x] Цвета дельт соответствуют правилу «хорошо / плохо» (отмены, CPL, CAC — снижение зелёное) — `metricMeta.test.ts`, `KpiCards.test.tsx`, страничные тесты
- [x] Экран читается на 1600×1000 без горизонтальной прокрутки — проверено в браузере (`scrollWidth = 1600`), обе страницы помещаются по высоте

Остальные требования ТЗ: фильтры «Период» (месяц, квартал, с начала года, произвольный), «Филиалы», «Каналы»; сравнение «с прошлым годом» / «с планом»; время обновления в шапке; формат (₽, млн ₽ с одним знаком, пробел-разделитель); KPI со спарклайном и дельтой; кросс-фильтры (филиал, направление, канал).

**Трактовки ТЗ:** ROMI считается по выручке первого визита нового клиента (по умолчанию в ТЗ), атрибуция — «последний значимый канал», остальное — разделы «Зафиксированные трактовки», «Трактовки сессии 3» и «Трактовки сессии 4».

## Что осталось за кадром

- Клик по этапу воронки открывает только тост: список заявок этапа — вторая очередь (в ТЗ «по желанию»).
- Фильтр филиалов для заявок, расходов и веб-аналитики: нужен филиал в этих наборах данных.
- Тепловая карта на моках контрастнее эталона, масштаб «Источников записи» (≈ 20 тыс. против 2–3 тыс. на скриншоте) и CAC отличаются от скриншота — всё это свойства мок-данных, а не вёрстки.
- Реальные источники данных вместо генератора, подсветка ячеек тепловой карты с клавиатуры.
